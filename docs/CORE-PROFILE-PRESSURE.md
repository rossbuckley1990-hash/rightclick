# Fresh Core Profile AI — real Kafka boundary

This increment moves from deterministic seven-operation engineering transcripts
to a real fresh AI performing a bounded external effect. It is one substrate,
not completion of G13/G17 or release acceptance.

## Actual client boundary

The existing catalogue pressure test found 20 inherited tools, then 14, then 8,
before thread-scoped switches and an isolated model catalogue produced exactly
the seven canonical RIGHTCLICK operations. Its six required RED→GREEN dimensions
are documented in `evidence/core-profile-isolation-20261007/CORE-PROFILE-ISOLATION.md`.

For this run the same client was copied to a neutral private working directory;
the runtime was a private immutable copy of candidate executable SHA-256
`3c6fd8d48c381646d7da41f0864d853735d9489cbec7b21e2dbfa3c1191d2bd2`
(built from source `242e97d`). Provider credentials and signing-key bytes were
host-owned protected files; the model received no such bytes.

Before inference a local request capture confirmed the actual current outgoing
catalogue contained only the seven canonical functions. Native Codex represented
them in an `additional_tools` functions namespace rather than the request's
ordinary `tools` list. The first harness incorrectly counted only that empty
list and stopped before AI inference. This is preserved as a harness error,
not invented RIGHTCLICK RED evidence. The corrected validator flattens both
declared locations, checks the namespace and rejects any eighth operation.

The subsequent real gpt-6.1-sol inference used native sign-in and the official
provider, with the same isolated catalogue/settings. Its production inference
request was not intercepted: outgoing catalogue evidence comes from the matched
local capture, while actual model-selected calls come from the live inference
transcript. This distinction is intentional.

## Observed execution and independent evidence

The actual AI called runtime, providers, inspect, actions and explain, then
`context_run` without confirmation. It observed `awaiting_user`, invoked the
same discovered capability once with confirmation, and read `context_run_status`.
No mutation retry occurred. The broker high-watermark increased by exactly one.

The confirmed operation produced one exact UTF-8 record, including the requested
newline, on the isolated `rightclick.proof` topic, partition 0, offset 13.
A separate scoped consumer read that record and checked its key/value plus the
host's `rightclick.invocation` header. The header exactly matched RCIR task
`08322506-4B43-407F-8731-7095F7175206`.

An independent Python Ed25519 implementation verified the receipt against a
separately provisioned, pinned public key and checked the exact signed task,
lease and succeeded outcome. The entire decoded signed observation matched the
independent consumer's topic/partition/offset/key/value/timestamp/invocation ID.
The model itself correctly reported that it had not independently checked the
signature; the workbench did that check after its run.

Kafka issuer ACLs constrain publisher/observer topic rights. Exact record
arguments, resource, contract and single-use invocation are local RCIR constraints;
this does not claim the broker issued a credential confined to that individual
record. The provisioned proof signing key is not a production trust/key lifecycle.

Raw captures, actual calls, immutable binary identity, external readback, receipt,
public key, independent verification and original/archive hashes are retained in
`evidence/core-profile-isolation-20261007/fresh-ai-kafka/`. A check against the
current Kafka password materials found no exact raw matches in these files;
the programme's broader secret-leak/adversarial requirements remain separate.

Provider removal/restoration, streams, delegated authority, native Windows/Linux,
all eleven substrates and final installed release bytes remain RED for this AI
experiment. No new AI-facing operation or provider-specific tool was added.
