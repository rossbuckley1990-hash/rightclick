# Capability lease authority and reservation design

Written before implementation on the isolated portable baseline `d496cf1b240bc97a52dbb5a5a76f378fd183b074`.

A lease is an immutable Codable body whose canonical bytes use `CapabilityValue` under the `RIGHTCLICK-CAPABILITY-LEASE-1` signing domain. It binds an issuer Ed25519 public key, enrolled subject runtime and public key, exact environment UUID, issuing execution, optional parent lease UUID and SHA-256 digest, finite issued/expiry times, 32-byte nonce, exact capability/profile/network sets and every finite quota. An envelope signs the body with the existing RCIR Ed25519 interfaces. Its embedded issuer is a locator; verification always requires an independently pinned issuer, expected subject and expected environment. Signature verification is never proof that a bearer possesses the subject key; admission takes the key and environment established by authenticated Link enrollment/session validation.

All limits are explicit. Hard bounds agree with the environment model: delegation depth 2, one-hour maximum lease duration, 4 CPU, 4096 MiB memory, 1,000,000 micro-usd; execution, child and descendant quotas additionally have finite fixed maxima. Zero quota denies an operation; no sentinel means unlimited. Canonical identifiers and exact network origins reject wildcards, aliases and unknown structures. Codable input is validated again at verification/admission, so decoding cannot bypass constructor validation.

`CapabilityLeaseReservationState` is a pure Codable candidate state for the Core protected durable transaction. It stores complete signed leases, remaining budgets, parent links, revocation state, monotonic observed-clock high-water and invocation reservations. Core must copy this state, perform a transition, atomically persist the candidate, and only then dispatch an effect. This type neither asserts durability by itself nor exposes cloud dispatch. An admission result identifies whether a reservation was already present, so a resumed request reconciles its existing effect instead of dispatching a second time. Expiry, rollback, revocation, lineage and subject checks also apply to retries.

Delegation authenticates the parent's subject through Link, verifies the child signature under that pinned subject key and binds both parent UUID and exact signed body digest. Capability, profile and network sets can only shrink; expiry and resource ceilings cannot increase; delegation depth must strictly decrease. A child receives an allocation from its immediate parent's *remaining* execution and cost budgets. Direct-child capacity costs one, and descendant capacity reserves `1 + child.maximumDescendants`; child allocations are therefore disjoint subtrees. The parent has already reserved that entire subtree allocation from its ancestor. Grandchild admission consumes the child's own allocated capacity rather than double-debiting its ancestor. Two siblings cannot each receive the original full parent budget. Reserved allocations are not refunded after an external effect fails or is unknown.

Invocation admission requires an exact allowed capability/profile, network-origin subset, bounded shape and nonnegative integer cost. It subtracts one execution and the conservative cost reservation before dispatch. The reservation ID is bound to the request digest and every admission field. Reusing an ID with changed intent fails. A successful retry reports an existing reservation and spends no second quota; existing Link replay and Core effect reconciliation still prevent duplicate dispatch.

Revocation walks persisted parent relationships at admission, so revoking any ancestor immediately invalidates every descendant without deleting audit records. The journal retains allocations and reservations after revocation/expiry. Registration capacity is finite and fails closed. Each transition validates persisted structure and budgets before modifying a candidate; thrown transitions leave their original value unchanged. Clock high-water is committed with successful admissions, preventing a later time rollback from extending authority after restart.

Tests exercise production canonical signing, verification and pure reservation transitions with Ed25519 keys, signed-field mutations, unpinned signers, subject/environment mismatch, expiry/rollback, scope/resource/cost widening, depth exhaustion, cumulative sibling quota exhaustion, reservation conflicts/retries and ancestor revocation. Durable write-before-effect enforcement remains the Core coordinator's responsibility.
