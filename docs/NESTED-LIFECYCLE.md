# Durable nested lifecycle and reconciliation

`EnvironmentCoordinator` extends the portable Core. Its installed provider implements the Protocol contract; no provider-specific tool is introduced. Root operator pins, approved runtime profiles, finite profile ceilings, and the enrollment verifier are host configuration. An environment URI carries no authority. The existing engine retains RCIR admission, contextual discovery, confirmation, and semantic outcome adjudication.

The coordinator's default lifetime ledger admits at most two environment creations and reserves at most 1,000,000 micro-USD across all of them. These limits may be tightened or explicitly configured by the host within finite hard ceilings. Records, resource cost reservations, child counts, proof replay records, and dependency consumption are never refunded after ambiguous effects. Child lifetime must fit its parent environment and every signed ancestor lease. This deliberately conservative ledger rejects new work when capacity is exhausted; it preserves cleanup and audit records instead of recycling replay state.

## Write-ahead lifecycle

The protected `EnvironmentJournal` retains complete Codable state. A successful transaction flushes the intent and quota transition before provider dispatch. The implementation uses protected directories and files, no-follow opens, an interprocess lock, atomic rename, fsync, an installation marker, and an external custody anchor. Missing, replaced, corrupt, or unsafe history rejects work. Recovery authenticates signed leases and enrollment certificates under the original installed host keys, reconstructs cumulative creation counters from retained lineage, and checks dispatch ownership and workload bindings.

Creation reserves a host environment UUID, correlation UUID, immutable lineage, specification, expiry, execution identity, request digest, and cost. A matching retry returns and independently observes that same intent. A conflicting retry rejects. Even if the provider accepted creation before a crash or timeout, Core never blindly replays `create`; it observes the retained correlation. A crash after reservation but before dispatch can therefore leave a permanently uncertain tombstone. That is a deliberate safety tradeoff against duplicate paid resources.

Provider acceptance and independent presence are separate stored facts. A present observation pins the resource locator. An observation exception, timeout, identity mismatch, or partition records `unknown`, never absence. Provider creation or bootstrap acceptance cannot enroll a runtime. Bootstrap reserves one short-lived, single-use enrollment ID and a random 32-byte challenge before dispatch. The host-installed verifier must produce a signed parent enrollment certificate; Core checks its signature, exact handle, manifest, enrollment ID, challenge, freshness, expiry, and any separately observed runtime facts before atomically consuming it and activating the runtime key. The complete certificate remains retained after revocation.

## Authority and workload evidence

Admissions are opaque host-issued values tied to one coordinator. Root admission uses installed operator authority. Authenticated child admission binds the actual Link subject key, enrolled runtime, environment, and signed lease. The integration derives the request digest from actual canonical arguments and the requested postcondition. Discovery is checked again at dispatch. Effect methods require host-confirmed approval; caller arguments cannot construct admissions or choose provider credentials, profiles, or an enrollment verifier.

Only a depth-zero environment can receive a root lease. A descendant receives a lease through its authenticated parent's signed delegation. Core verifies attenuation and durably consumes execution, child, descendant, and cost allocations before any effect. Ancestor expiry and revocation remain active checks. Additional creation counters charge each ancestor's descendant quota before creation, so a child cannot create an unpaid-for resource and only later ask for delegation.

Every installed or delegated lease must cover the actual enrolled environment's profile, CPU, memory, cost unit, and bounded whole-environment cost. Each non-creation effect reserves the actual target profile and CPU/memory requirements. Its incremental cost charge is zero because the whole bounded VM cost was already reserved at creation; the implementation does not claim a separately isolated 128-MiB process inside a larger VM. No cgroup/process limit is inferred from a lease.

Enrolled identity is checked against fresh independent provider runtime observations. A changed key, changed executable manifest, or positively stopped runtime permanently revokes authority; the original enrollment certificate and completed receipts remain retained. A missing, stale, unavailable, or non-ready runtime observation suspends effects until the original exact identity is independently observed ready again. The workload refreshes these pins immediately before reservation and dispatch under the shared broker lock; it never silently enrolls a successor key.

The only workload is the approved challenge operation. Execution reserves a fresh nonce, exact execution/request/runtime/key/lease pins, and a deadline before dispatch. Provider acceptance remains `accepted` until a separate observation reads the exact challenge. A different observable value is `failed`; an unavailable or expired read is `unknown`. Signed child reports identify a reporting key and protect exact invocation bytes; they do not decide semantic success.

The existing engine finalizes the caller's complete requested postcondition before the production source requests a proof certificate. Core persists an immutable digest of that entire finalized `ExecutionRecord`. Later provider observations, direct challenge readback, reconciliation, retries, and proof retention cannot rewrite it. A failed, unknown, or otherwise unsuccessful engine finalization cannot produce an authoritative success certificate. Direct Core use without an engine finalization may explicitly adjudicate the built-in challenge predicate; that predicate receives its own immutable finalization before its certificate is published and cannot later become a different caller request.

Proof admission authenticates the pinned child key and exact retained execution binding and durably consumes its sequence before independent observation and host certificate finalization. A crash during finalization preserves an unresolved proof reservation and does not make the proof reusable. Complete signed proof and host certificate bytes remain available for audit without modifying the finalized execution digest.

Host-installed causal prerequisites select locally retained signed proof and host certificate records; callers cannot supply substitute proof bytes or trust keys. Admission requires the earlier complete final outcome to be succeeded and validates exact execution/environment/request/predicate/observer binding and freshness. Up to eight prerequisites can be bound to an opaque admission and its canonical consumer request digest. One-use consumption is flushed before dispatch, and freshness, complete final outcome, and exact consumer reservation are checked again inside the effect's journal transaction and immediately before dispatch. The exact retry is idempotent and another consumer rejects. The retained dispatch also records its selectors and admission time so recovery validates historical causal admission without requiring old evidence to remain fresh forever.

## Recursive teardown

The first teardown transaction revokes the entire recorded subtree's leases and active runtime authority and persists separate stop and destroy operation UUIDs. Only then can the first provider effect occur. Reconciliation can perform this safety cleanup after user or child credentials have expired; it cannot create, bootstrap, run workloads, or target an unrecorded resource.

Teardown visits direct children recursively. Each descendant must have an exact independent absence observation before the parent receives stop or destroy. A delete response alone cannot mark the resource destroyed. Accepted-but-still-present deletion retains a cleanup target. A partition retains the same operation IDs and an uncertain state; reconciliation after recovery re-observes the correlation, reuses idempotent stop/delete keys where still present, and resumes deepest-first. If a parent has already disappeared while descendants remain, its absence is retained but its terminal destroyed status waits for descendant absence.

An accepted asynchronous create can become visible after an earlier exact absence observation. Core pins a returned non-secret resource locator separately from existence, retains terminal records, and continues to observe those records during reconciliation. If the exact retained environment/correlation/resource identity reappears, the row reopens only as revoked cleanup: runtime authority stays absent, leases stay revoked, and subtree stop/destroy intents are durably flushed before cleanup. A changed resource identity is never adopted. Historical finalized receipts and previously consumed creation/cost budgets remain unchanged. The deterministic delayed-adapter barrier tests complete the original accepted operation once after absence and exercise cleanup both directly and after broker recovery; they do not dispatch another create or claim live-cloud evidence.

If an uncertain create returned no locator, a subsequent absence observation remains `unknown` and revoked, with durable cleanup intents. It cannot become a terminal unbound tombstone that excludes later cleanup. A later exact observation under the original retained environment/correlation intent can establish its first locator only for cleanup, using those same stop/destroy IDs; runtime authority and leases cannot revive. Direct and recovered broker barrier tests cover this path without replaying creation, changing historical finalized receipts, or refunding budgets.

The last independently observed present identity is retained separately. Providers supporting the narrow host-only recovery interface can restore their authenticated exact resource binding from the protected ledger, allowing a subsequent exact-resource absence query after adapter restart. Arbitrary provider inventory entries are not adopted or deleted. Inventory detects duplicate/mismatched retained correlations; unsafe duplicates reject instead of being treated as a successful handle.

Execution status is durable and uses existing `ExecutionRecord` semantics. Receipt ownership is the authenticated dispatch owner's pinned environment/runtime/key; revocation prevents new effects without erasing access to that owner's historical receipts. Root operator status access uses the installed host boundary. Teardown preserves all enrollment, lineage, intent, dispatch, and signed evidence history.

## Limits of the demonstrated guarantee

The deterministic provider exercises production coordinator admission and reconciliation but does not prove a Linux process or cloud VM executed. Real-cloud evidence requires the opt-in production adapter path and actual configuration. Core refuses creation unless the installed provider declares enforceable TTL support; a local timer or caller flag cannot supply that guarantee. Provider observations remain an explicit trust boundary, and software enrollment does not claim hardware attestation or protection against a compromised environment lying about its internal process.

The protected journal holds the same process-shared lock across durable reservation, fresh admission checks, provider dispatch, and observation. Another broker cannot destroy or revoke a reserved resource during the dispatch gap. A process crash releases that OS lock while leaving its flushed intent recoverable. Native provider idempotency and enforceable TTL remain necessary for requests that have already reached an external API; a local lock cannot retract such a request after the process dies.

Opaque pending creations whose provider cannot independently establish existence or absence remain uncertain. The coordinator cannot fabricate cleanup success for such a resource. It likewise cannot discover resources that lack its retained ownership/correlation markers. These limitations are retained in status and must be considered during live deployment review.
