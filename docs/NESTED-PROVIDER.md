# Environment providers

The provider-independent `EnvironmentProvider` contract lives in `RightClickProtocol`. The coordinator supplies a previously admitted, durably reserved intent or handle. Provider acceptance, resource observation, runtime identity and workload verification remain separate. None of these adapters adds a public MCP operation. Provider selection, credentials, app, image and workload implementation are operator choices on the execution node.

## Deterministic default

`InMemoryEnvironmentProvider` is the default integration substrate. It models resource reality independently from acceptance. Its host-only faults cover a partition, creation accepted before the response is lost, bootstrap accepted without a runtime, deletion accepted while the resource remains present, workload acceptance without an effect, a wrong independently observed challenge, a wrong runtime manifest and a dishonest child report. It retains immutable correlation tombstones; retrying a destroyed intent never recreates a resource. Unknown correlations reject rather than inventing absence. Every resource has a bounded lifetime under the injected substrate clock, and expiration clears its simulated runtime identity and challenge observations.

Bootstrap generates an ephemeral Ed25519 key inside the simulated node. Observations export only the public identity. Typed `signedRuntimeClaim` and `signedExecutionProof` helpers check the active handle, manifest, key, environment, lineage and lifetime before signing. Challenge proof signing additionally requires the recorded `environment:execute` execution and its configured child report. `signedCapabilityLease` keeps issuer A's key inside A and signs only for active direct child B with the exact B runtime/key and bounded lifetime; installation still requires complete attenuation against the coordinator's persisted parent lease. These helpers are host integration fixtures: they establish signed simulated reports, not a Linux VM, a process, a remotely executed binary or a cloud result. Separate observer paths compare the actual observed challenge against host-owned expectations.

## Reference provider choice and configuration

The lead inspected the execution node before choosing the reference provider. The Fly and AWS credential/configuration locations checked were absent. Fly Machines was chosen as a small disposable Linux VM API, beneath the generic abstraction. No cloud credential was acquired and no live cloud resource was created.

The Fly adapter uses the fixed TLS origin `https://api.machines.dev/v1`. The vendor documents app-scoped [create, get, start, stop and delete operations](https://fly.io/docs/machines/api/machines-resource/), [metadata and deleted-resource listing](https://docs.machines.dev/machines/Machines_list), and an [exec endpoint with an argument array and standard input](https://docs.machines.dev/machines/Machines_exec). The adapter implements those request/response paths with a bounded transport; requests have a five-second deadline and responses a one-MiB cap. Redirects, response URL changes, cookies, inherited URL credentials and cached responses are rejected or disabled. A transport exception or malformed/authentication response remains unavailable/unknown, never absent or succeeded. Provider response bodies and network errors are not returned as diagnostic messages.

An operator constructs `FlyEnvironmentProfile` with a fixed app and region, canonical host ownership ID, named profile ceiling, expected Linux x86_64 runtime manifest, a registry image pinned by SHA-256 digest, and a conservative integer micro-USD rate covering the full shape and any ancillary charges. The request cannot supply an endpoint, registry, image, credential, shell command, volume or service. Tags such as `latest` are rejected. CPU, memory, absolute expiry and ceiling cost are checked before dispatch, with overflow-safe arithmetic. Cloud costs that cannot be covered conservatively must reject admission.

Credentials are injected by a node-local closure. The token is used only in the cloud HTTP authorization header and is never encoded in intent metadata, child environment, bootstrap input, acceptance, observation, proof or error. The image process is configured to ignore app secrets, has no supplied secrets, no services and no mounts. This prevents the adapter from forwarding parent or app credentials into a child. Operator review must independently verify the actual approved image and app configuration before installation.

## Hard lifetime and uncertain creation

Fly documents `auto_destroy` as cleanup after completion, and [restart policy `no`](https://fly.io/docs/machines/guides-examples/machine-restart-policy/) as preventing restarts after the main process exits. Neither is a hard VM lifetime limit if the guest hangs or is compromised. The adapter therefore has no default live creation or recursive execution support and reports `enforcesTTL == false`.

Creation requires an installed `FlyEnvironmentCreationGuard` whose production implementation independently enforces the exact provider-visible lifetime even after parent and guest failure, checks the approved profile and total spend bound, and durably reserves at-most-once dispatch before returning. A configuration Boolean, a guest environment variable or a local parent timer does not satisfy this contract. This repository supplies no such production guard. Test guards are identified as simulations. An audited provider-visible external janitor with bounded deletion delay and a conservative cost allowance is a possible implementation, subject to independent verification; it is not claimed here.

Before a POST, the adapter queries owned resources for the exact correlation. Metadata carries host ownership, canonical environment/correlation IDs, the canonical intent digest, a non-secret intent encoding and pinned image. A match must agree on the full immutable lineage/spec/expiry before binding. Ambiguous duplicate correlations fail closed. There is no documented native create-idempotency assumption. Once creation has been reserved/dispatched, a lost response or empty listing never permits a blind second POST; the original intent must be reconciled. A reopened adapter depends on the same protected durable guard and coordinator ledger.

Presence comes from an authenticated exact resource read after the complete marker binding. Delete acceptance or a state string `destroyed` is insufficient. Absence requires an authenticated exact 404 for that bound resource. An empty listing, an unknown correlation, a timeout, a 403 or a changed identity cannot prove absence. On adapter restart the host may restore a previously authenticated present binding from its protected ledger; the recovery method is host-only and must never accept caller-supplied observations. Deleted-resource listing assists recovery where the provider retains the marker; it does not replace durable host history.

## Runtime artifact contract and remaining gates

The adapter's fixed helper contract is `/usr/local/bin/rightclick-environment-runtime`, supplied inside the approved digest image. The `serve` process must own ephemeral key generation, expire its session, enforce its installed policy and exit at its deadline. `bootstrap`, `challenge`, `observe-runtime` and `observe-challenge` receive bounded JSON through standard input; the adapter never interpolates a shell command. The helper must enforce immutable execution ID/challenge idempotency on its own protected runtime storage. Child enrollment and lease authorization remain Core/Link responsibilities. The cloud parent token is not supplied to this helper.

Runtime observation requires the exact environment, pinned manifest, 32-byte public key and a fresh timestamp. Workload observation requires the exact environment and execution IDs and the independently read value. Exit zero and HTTP 200 only permit parsing the response; semantic adjudication still requires the host's fresh exact challenge and signed proof checks. The provider observation trust boundary is the authenticated cloud API and guest helper, not hardware attestation; a compromised cloud provider remains outside that guarantee.

This repository does not supply or audit a runnable helper image, a production lifetime guard or a provider spend quotation. Live creation is consequently unavailable by default. Unit tests exercise the actual Fly adapter with injected transport and guard fixtures, including request construction, credential isolation, uncertainty, correlation binding, redirects, cost bounds and exact 404 handling. They do not establish cloud execution. A live integration run must explicitly install and verify the approved artifact, guard, local credentials and bounded profile first, then demonstrate bootstrap, challenge, fresh signed enrollment/proof, recursive teardown and exact verified absence. No live test result is claimed.

The checked-in opt-in test `EnvironmentLiveCloudTests.testOptInFlyAuthenticatedObservation` performs only an authenticated, read-only resource listing. Enable it with `RIGHTCLICK_NESTED_LIVE_FLY_OBSERVE=1` and node-local `FLY_API_TOKEN`, `RIGHTCLICK_NESTED_FLY_APP`, `RIGHTCLICK_NESTED_FLY_OWNER` (canonical ownership UUID), `RIGHTCLICK_NESTED_FLY_IMAGE` (digest-pinned image), and `RIGHTCLICK_NESTED_FLY_EXECUTABLE_SHA256`. `RIGHTCLICK_NESTED_FLY_REGION` defaults to `lhr`. It creates no resource and proves no bootstrap, isolation, workload, nesting, or cleanup. Without opt-in it is explicitly skipped. No credentials were available for this task, so even this read-only live gate remains unexecuted.
